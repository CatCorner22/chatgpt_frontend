# Protected release checks

Run the same release command as the pull request check from a clean checkout with Git, Python 3, Node 24 and Chromium. The Worker and browser fixtures use temporary local services and test identities.

```sh
npm ci
npm ci --prefix north-star-kit
CHROMIUM_PATH=/usr/bin/chromium npm run test:protected-release
```

The Worker uses the compatibility date in [nitro.config.ts](../nitro.config.ts). When upgrading that date, verify the packaged Worker starts with the locked runtime. The workflow installs Chromium through the locked Playwright version. To use that browser locally, run `npm exec --no -- playwright-core install chromium` and set `CHROMIUM_PATH` to the path printed by `node --input-type=module -e 'import { chromium } from "playwright-core"; console.log(chromium.executablePath())'`.

## Approval and branch settings

Keep a protected original available when exploring a variation. Identify each proposed removal, replacement of a protected design or artwork, or weakening of a safeguard in the pull request. Show the change to Blake, record explicit approval for the named items, then update the relevant baseline and test in the same reviewed change. A passing run only establishes the automated results. [Project instructions](../AGENTS.md) · [Pull request template](../.github/pull_request_template.md)

The workflow runs on pull requests, merge queues, pushes to the release branches and version tags, and manual dispatch. Its GitHub token has read access to repository contents. The checked-in CODEOWNERS file requests review by the repository owner account, `@CatCorner22`, when a covered path changes. An administrator must confirm that handle represents the intended approver and has the required write access. [Workflow](../.github/workflows/protected-release.yml) · [Code owners](../.github/CODEOWNERS)

After these files land on the target branch and the check has run, configure a GitHub ruleset or branch protection on `main` and any branch used for release, including `north-star/garden-to-delivery`. Require a pull request, an approving code-owner review, dismissal of stale approvals on new commits and the **Protected release checks** status check from GitHub Actions. Apply the rules to administrators and restrict bypasses. Protect release tags separately if tags initiate a release. Repository files alone cannot activate these settings or block a release outside GitHub. [GitHub code owners](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/customizing-your-repository/about-code-owners) · [Protected branches](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches)

GitHub requires someone other than the pull request author to approve. With a single code owner, an authorized contributor can open the pull request and request the owner’s review. If the owner authors protected changes, the repository needs a second reviewer explicitly authorized by the owner before that person is added to CODEOWNERS.
