# Next.js source-trial assessment

**18 November 2026 (UTC). Official documentation reviewed and an owned production fixture exercised.** Focus continues to offer the developer-guided path for Next.js. The fixture used the existing Vite-labelled source-trial transform. Its dependencies were installed in a temporary project, and Focus's source and dependencies stayed intact.

A separately versioned App Router adapter is a candidate for a bounded source-shape proposal. Focus currently accepts two source files and generates a styling patch. Framework identity and runtime behavior require separate evidence.

## Current documented baseline

The official documentation selector displayed **Latest v16.4.6** when inspected. The owned fixture below pins that same version. The [official support policy, Supported Versions](https://nextjs.org/support-policy#supported-versions) lists 16.x as Active LTS and 15.x as Maintenance LTS, with the latter's maintenance extended through 31 January 2027. It distinguishes stable/LTS releases from the canary channel and does not recommend canary for production traffic.

The [installation requirements](https://nextjs.org/docs/app/getting-started/installation#system-requirements) state Node.js **20.9 minimum**; [TypeScript setup](https://nextjs.org/docs/app/getting-started/installation#set-up-typescript) states **5.1.0 minimum**. Installation guidance identifies Turbopack as the default and describes `--webpack` as an alternative. These are documented minimums and build choices, not proof that a particular lockfile, Node release, or custom configuration is compatible. The same page says Next.js 16 builds do not automatically run linting.

## Smallest candidate worth proving

The following are proposed Focus limits, not restrictions imposed by Next.js:

1. Accept exactly one parameterless, synchronous, named default TSX root page with an existing top-level `use client` directive, plus its directly imported sibling plain CSS module. The initial candidate paths are exactly `app/page.tsx` or `src/app/page.tsx`, as defined in the [proposed boundary](../superpowers/specs/2026-11-18-next-source-trial-boundary.md). Nested routes, route groups, dynamic segments, layouts, other components and special route files require explicit later handling rather than silently relaxing path validation.
2. Preserve an existing top-level `use client` directive and every import. For the initial interactive shape, define state and handlers inside an explicit client module. A simple synchronous Server Component would need its own fixture and evidence. Keep async pages, server-action forms, and ambiguous component trees on the developer-guided path.
3. Keep the existing explicit native wrapper, heading, body and action roles, static class references, bounded style-property grammar and retained page background. Keep native anchors/buttons as the initial action scope. Leave `Link`, `Image`, custom components, Tailwind utilities, global CSS, Sass, CSS composition and unmodeled state/cascade forms outside it until separately designed and proven.
4. Change only the declared wrapper-class insertion and appended CSS. Preserve content, accessibility attributes, destinations, event handlers, data expressions and all noneditable source spans. Retain exact before/after identity checks and selective inverse patches. A preserved source span is evidence about the patch, not proof that the whole application behaves identically.

## What the two files cannot establish

- The actual Next/React versions, App Router installation, lockfile, compiler/bundler configuration, lint/type-check settings, or deployment target.
- The required root layout, parent client/server boundaries, serializability of real boundary props, imported behavior, authentication, data services, server actions, or hydration results. The [installation page's app-directory section](https://nextjs.org/docs/app/getting-started/installation#create-the-app-directory) separately requires the root layout; it is outside this pair.
- Outer CSS, font setup, shared module consumers, route transitions, loading/error states, or whether a native-looking action's destination exists and is appropriate.
- An isolated runtime, absence of external effects, customer build success, usability, visual improvement, deployment, or completed rollback. Do not infer these from parse success, a directive, a hash, or a package label.

## Evidence still needed before enabling a Next.js adapter

Implement and verify a specific Next.js eligibility check and adapter identifier across preparation, packaging, and verification. Test supported client-route pairs and refusal cases while preserving directive and import order. Repeat the owned baseline, forward, and inverse proof using that adapter. The observed experiment covers Next.js 16.4.6 with Turbopack only.

Exercise the owned client's hydration, invalid input, pending state, success, failure and retry, and retained values. Inspect rendered appearance, keyboard focus, and narrow widths in a supported browser. Verify refusal on stale touched files under the new adapter. Customer behavior and suitability require a separate isolated trial in the customer's own project.
