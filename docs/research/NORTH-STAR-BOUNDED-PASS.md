## An operational formula

Let `x` be one proposed redesign and `c` the actual customer context. First determine whether each promised safety/task requirement has current evidence:

`eligible(x, c) = every required gate is passed by relevant, revision-bound evidence`

An unknown, unrun, failed or stale required gate is not eligible. A documented, justified non-applicable requirement is different from a pass. The model is a proposed decision policy; a complete evaluator is not introduced by this document.

For eligible candidates, compare a vector rather than one compensating average:

`Q(x, c) = [task success, comprehension, visual craft, accessibility, reliability, performance, transfer fidelity]`

Compare `Q(Focus, c)` with `Q(human reference, c)` using the same brief, content, task and evaluation conditions. Choose the practical margins and methods before looking at results; do not invent universal weights or percentages. A beautiful screen cannot compensate for a broken save, and a passing build cannot establish visual craft. A small pilot can reveal failures and guide repair without proving population-level equivalence.

The repeatable loop is:

1. Record the task, protected behavior, baseline and support boundaries.
2. Identify one specific shortfall and its likely mechanism.
3. Choose a bounded change and define the expected observable outcome.
4. Build it in an isolated preview with exact change/undo information.
5. Repeat the original task and affected failure/recovery cases.
6. Compare craft on matched content; keep preference separate from task evidence.
7. Repair the observed failure, preserve the previous result and rerun affected checks.
8. Advance only the claims supported by the new evidence.

## Stop broad research; prove one customer journey

The highest-value next increment is one existing-project transfer rehearsal from baseline through upgrade and selective undo. Use the adapter Focus actually supports: the strict React/Vite TSX and CSS-module pair. The user's intended GitHub/React/Next.js destination is broader; current support must not be silently extended to arbitrary Next.js or repositories by instructions alone.

Prepare a fixture with real content, a consequential main task, meaningful empty/error/loading states and a protected unrelated edit. A fresh LLM recipient receives the actual package and makes only the proposed change. Check the raw returned files, build/test output, rendered preview, keyboard task, failure recovery and selective undo. Retain exact artifact identities and the recipient's actual assistance/commands. A returned-file byte match remains only a file match, not repository, deployment or usability evidence.

Then compare that result with a human-designed reference on the same content. Record where Focus loses: composition, type, imagery, affordance, state behavior, responsiveness or transfer. Implement the smallest repair that addresses an observed gap. Add a new adapter only with a declared support matrix and its own end-to-end evidence.

This is the recommended credit boundary: no more broad source collection unless a specific unresolved decision blocks that rehearsal. Additional reading alone will not settle whether a colleague can safely finish the workflow.
