# Worked planning journeys

Hypothetical examples, not observed customer results. All catalogue decisions remain proposals. Existing Focus entry points are identified separately from work assigned to a coding recipient.

## Existing appointment page: owner → coding recipient → visitor

1. **Goal, G01/G04.** The owner names the task: select a service, see its price, and request an appointment. Capture the working request behavior, validation, authentication and original files before a style trial. An unknown framework is an unresolved adapter prerequisite, not implied support.
2. **Content, C01–C05.** The owner approves service names, prices, availability qualifications and the actual request action. Preserve exact approved wording. A coding agent reports a wording conflict instead of quietly rewriting it.
3. **Plan, P01–P04.** Put service, price, time and request in a meaningful reading order. The owner can compare a concise page with a multi-section page; the choice affects scanning and later state handling. Both need the same real task checks.
4. **Direction/craft, D05/F01.** Open Focus's existing Stratosphere palette/font groups for bounded visual choices. These are actual controls. The rest of the catalogue is planning guidance. A font change affects line breaks, real weights, language coverage and button widths. Repeat those observations on the resulting artifact.
5. **Behavior, B03–B07/B09/B15.** The developer selects an inline request form. Its check uses ordinary document navigation, not a modal focus trap. Define waiting, success, failure, timeout and retry. A server-confirmed request is distinct from a button click or download.
6. **Responsive, R02/R07.** This page has no table: `hasTables=false` makes the table branch inapplicable with a reason. Review the form at narrow widths and zoom. A failed request retains entered values and explains how to retry; it cannot display a booking confirmation.
7. **Handoff, H01–H15.** For the current strict source trial, provide the supported React/Vite TSX + CSS-module pair, not an arbitrary Next.js project. Inspect exact forward/inverse changes in a separate project copy. The recipient runs the project's build and original appointment tasks. A mismatch returns to the proposal; no forced rewriting.
8. **Check, V01/V04/V05/V10/V12.** The reviewer compares the original and changed request flow. Record actual results and unrun checks against the exact revision. If request submission fails, retain the original deployment, fix the isolated change and repeat the failed task plus neighboring tasks. Reviewable drafts can be shared with open checks; a release decision requires the declared release evidence.
9. **Receipt and return, H12.** Focus currently records the owner's acknowledgment of a downloaded artifact. It does not observe a colleague's receipt or deployment. The owner returns to Garden to review evidence; merely visiting the final stop awards no completion.

## New editorial page

The owner supplies an article, image rights, useful alt text and a real subscription destination. Choose a reading order before a display font. Review body measure with the actual typeface: `ch` is the zero glyph's advance, not a character count. A single-language page still needs C10 language review. An ordinary subscription link still needs B01 native semantics. With no remote form, mutation or table, those state contracts are marked inapplicable with reasons, not tested successfully. An unknown subscription destination remains unresolved; the developer cannot invent one to make the page look complete.

## Concurrent work and a changed decision

The owner accepts a font change at artifact revision A. Record the selected option ID and actual values, plus the catalogue revision. Before the developer returns work, the owner changes the main action at revision B. Results produced for A cannot prove B. Compare the affected paths, resolve any conflict and repeat destination, label, wrapping and interaction checks. Preserve both attempts in history. A revert applies only when its recorded preconditions still hold; it must not erase the owner's unrelated B change.

## Local save and export

For a local editable draft, set `hasDraft=true`, `hasOperation=true`, `hasRemoteRequest=false` and select B12. Its selected path retains B04's completion obligation: a local write can fail, be canceled or finish after the user has moved on. H12 with `hasExport=true` also retains B04; an owner acknowledgment still differs from machine-verified completion or a colleague's receipt. Setting `hasOperation=false` in either context creates a planning conflict. Omitting the flag leaves context unresolved.

## Deliberately incompatible choices

G01.a with `hasExistingProject=true`, and G01.b with `hasExistingProject=false`, return `conflicting-planning-choices`. V12.a with H15.b does too: a release path cannot simultaneously use draft-only authorization. A compatible declared path returns `declared-constraints-satisfied`; it does not prove working UI, safe deployment or undeclared semantic relationships.
